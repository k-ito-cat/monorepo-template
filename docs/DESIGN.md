# DESIGN.md

## この文書について

この文書は、このプロジェクトにおけるデザインの上位仕様書です。

この文書は、次の2つを定義します。

- デザイン原則: デザイン判断の基準、情報設計の考え方、一貫性の前提
- デザインシステム: 上記の原則を、トーン、色、タイポグラフィ、余白、レイアウト、コンポーネント、インタラクション、文言などの設計ルールとして具体化したもの

この文書は、個別画面の詳細設計書ではありません。
画面ごとのレイアウト、個別コンポーネント仕様、詳細なユーザーフロー、実装コードやトークン値そのものは、必要に応じて下位文書または実装側で定義します。

人とAIの両方が参照できる、デザイン判断の共通の正本として扱います。

## 目的

- このプロジェクトにおけるデザイン判断の土台を明文化する
- 情報設計に関する一貫した判断基準を定める
- 後続のUI設計、画面設計、トークン設計、コンポーネント設計の前提をそろえる
- 人とAIが同じ前提で設計判断できる状態をつくる

## 適用範囲

- この文書は、デザイン判断の基準と、デザインシステムの設計ルールを定義する
- この文書は、個別画面の完成レイアウトや、個別機能に閉じた例外仕様は定義しない
- 下位のデザイン関連文書は、この文書の原則に従う

## 作成順序

1. DESIGN.md を定義する
   - 未定義項目が残る場合は、2 以降へ進まない
2. 必要要素を洗い出す
   - 要件から必要コンポーネントを洗い出す
   - UIパターンを洗い出す
3. 視覚化作業を行う
   - カラーパレットを作る
   - タイポグラフィスタディを作る
   - コンポーネントを作る
4. 画面設計を行う
   - 画面の一覧と責務定義を整理する
   - 画面遷移図を作る
   - 画面デザインを作る
5. 実装ルールを整理する
   - デザイントークン定義を整理する

## デザイン原則

### 基本原則

- 見た目より先に意味を整理する
- 装飾より先に構造を整える
- 変化より先に一貫性を優先する
- 印象より先に理解しやすさを優先する
- 局所最適より全体整合を優先する
- このプロジェクトのデザインは、視覚表現ではなく情報の明確さから始める
- デザイン判断は、理解しやすさ、見つけやすさ、迷いにくさ、予測しやすさに寄与することを優先する
- デザインは雰囲気を作るためではなく、情報と行動を適切に伝えるために存在する
- 表現上の個性は、構造と意味を損なわない範囲で扱う
- よくあるUIパターンを機械的に並べるのではなく、この業務や体験に合った情報設計から考える
- 理想的なモックではなく、実際に使われるプロダクトとして自然なUIを前提にする

### 情報設計と構造

- 情報は実装都合ではなく意味のまとまりで整理する
- 似ている情報は似ている構造で扱う
- 異なる目的の情報は明確に分ける
- 情報の階層は、利用者の目的と優先度に沿って構成する
- 主要な情報はすぐ把握できる位置と粒度で提示する
- 補助的な情報は主目的を妨げない形で提示する
- 情報量の多さではなく、理解しやすい配置を優先する
- ただ整っているだけの平均点の構成ではなく、情報の優先順位が明確な構成を目指す
- 画面内で何が主役なのかがひと目で分かる情報配置にする
- 「最初に見る → 次に比較する → 最後に行動する」という流れを意識して情報を配置する
- 構造は一目で大枠を把握できることを優先する
- 深すぎる階層や複雑すぎる分岐を避ける
- 同じ役割のものは同じ構造で現れるようにする
- 利用者が現在地、選択肢、次の行動を把握しやすい構造にする
- 一時的な例外のために全体構造を崩さない

### UIとUX

- 利用者が今どこにいて、何ができて、次に何が起こるかを理解できるようにする
- 行動の結果は予測しやすくする
- 重要な判断を隠れた前提知識に依存させない
- 不要な認知負荷を増やさない
- フィードバックは不安を減らし、状況理解を助けるものにする
- 可能な限り、操作はやり直しや見直しができるようにする
- 実運用を想定し、長いテキスト、欠損、異常値、ゼロ件、重複があっても破綻しにくい体験にする
- 視覚表現は構造と意味を補助するために使う
- 強調は装飾ではなく重要度に基づいて行う
- 情報の読みやすさと落ち着きを損なわない
- 繰り返し現れる要素は、文脈が変わっても同じように見え、同じように振る舞うようにする
- 状態や違いは明確に区別できるようにする
- 情報や装飾を盛りすぎず、本当に必要な要素に絞る
- なくても困らない装飾や要素は減らし、削ぎ落とした完成度を目指す

### コンポーネント設計

- 具体的な部品定義ではなく、部品設計の方針を定める
- 単発の見た目ではなく、再利用可能なまとまりを優先する
- 似た役割のものは、できる限り共通の考え方で扱う
- バリエーションは必要最小限にとどめ、役割の違いが明確に分かるようにする
- 新しい部品は、既存の考え方で対応できない場合にのみ追加する
- 部品名や分類は、画面固有ではなく役割に基づいて考える
- 状態の扱いは一貫させる

### 一貫性と言語

- 名称は実装都合ではなく意味に基づいて決める
- 同じ概念には同じ言葉を使う
- 違う概念に同じ言葉を使わない
- ラベルや名称は短く、意味が明確で、文脈に依存しすぎないものにする
- 文言は曖昧さを減らし、認識しやすさを高めるために使う
- 内部用語をそのまま利用者向け表現に持ち込まない
- 似た情報は似た見せ方で提示する
- 似た行動は似た位置、似た表現、似た流れで提示する
- 似た状態は似た手がかりで表現する
- 例外は最小限にとどめる
- 部分的に分かりやすく見えても、全体整合を崩すなら再検討する

### アクセシビリティと判断基準

- 色だけに意味を依存させない
- 強調や違いは複数の手がかりで伝える
- 読みやすさ、階層、状態の分かりやすさを基本要件として扱う
- キーボード操作やフォーカスの視認性を軽視しない
- エラーや補助情報は気づける形で提示する
- 一部の利用者だけが理解できる設計にしない
- 分かりやすさを優先する
- 意味の明確さを優先する
- 一貫性を優先する
- 再利用性を優先する
- 派手さより静かな使いやすさを優先する
- 思いつきより構造的な妥当性を優先する
- 見た目の美しさだけでなく、情報設計、優先順位、運用時の現実性、意味のある色設計を重視する

### 制約

- 装飾のためだけの表現を増やしすぎない
- 構造的な意味を持たない複雑さを持ち込まない
- 一度しか使えない見せ方を安易に増やさない
- 画面ごとの都合だけで命名や構造を決めない
- 重要度、状態、行動の違いが曖昧になる設計を避ける

- 状態の採用基準: 状態は汎用UIの一覧から機械的に当てはめず、実務上そのコンポーネントで実際に起こりうるものだけを採用する
