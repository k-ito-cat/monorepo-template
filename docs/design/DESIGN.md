# DESIGN

## この文書の役割

この文書は、`docs/design/` 配下のデザイン文書群における上位原則と入口を定義する。  
ここでは、デザイン判断の基準、文書群の責務、参照関係を扱う。  
具体的な値、個別画面の完成レイアウト、個別コンポーネント仕様は下位文書で扱う。

## 目的

- このプロジェクトにおけるデザイン判断の土台を明文化する
- 情報設計に関する一貫した判断基準を定める
- 後続の UI 設計、画面設計、トークン設計、コンポーネント設計の前提をそろえる
- 人と AI が同じ前提で設計判断できる状態をつくる

## 適用範囲

- この文書は、デザイン判断の基準とデザイン文書群の構成を定義する
- この文書は、個別画面の完成レイアウトや個別機能に閉じた例外仕様を直接定義しない
- 下位のデザイン文書は、この文書の原則に従う

## デザイン原則

### 基本原則

- 見た目より先に意味を整理する
- 装飾より先に構造を整える
- 変化より先に一貫性を優先する
- 印象より先に理解しやすさを優先する
- 局所最適より全体整合を優先する
- デザインは視覚表現ではなく情報の明確さから始める
- デザイン判断は、理解しやすさ、見つけやすさ、迷いにくさ、予測しやすさに寄与することを優先する
- デザインは雰囲気を作るためではなく、情報と行動を適切に伝えるために存在する
- 表現上の個性は、構造と意味を損なわない範囲で扱う
- よくある UI パターンを機械的に並べるのではなく、対象業務や体験に合った情報設計から考える
- 理想化されたモックではなく、実際に使われるプロダクトとして自然な UI を前提にする

### 情報設計と構造

- 情報は実装都合ではなく意味のまとまりで整理する
- 似ている情報は似ている構造で扱う
- 異なる目的の情報は明確に分ける
- 情報の階層は利用者の目的と優先度に沿って構成する
- 主要な情報はすぐ把握できる位置と粒度で提示する
- 補助的な情報は主目的を妨げない形で提示する
- 情報量の多さではなく理解しやすい配置を優先する
- 平均点の構成ではなく、情報の優先順位が明確な構成を目指す
- 画面内で何が主役なのかがひと目で分かる情報配置にする
- 構造は一目で大枠を把握できることを優先する
- 深すぎる階層や複雑すぎる分岐を避ける
- 利用者が現在地、選択肢、次の行動を把握しやすい構造にする
- 一時的な例外のために全体構造を崩さない

### UI と UX

- 利用者が今どこにいて、何ができて、次に何が起こるかを理解できるようにする
- 行動の結果は予測しやすくする
- 重要な判断を隠れた前提知識に依存させない
- 不要な認知負荷を増やさない
- フィードバックは不安を減らし、状況理解を助けるものにする
- 実運用を想定し、長いテキスト、欠損、異常値、ゼロ件、重複があっても破綻しにくい体験にする
- 視覚表現は構造と意味を補助するために使う
- 強調は装飾ではなく重要度に基づいて行う
- 状態や違いは明確に区別できるようにする
- 情報や装飾を盛りすぎず、本当に必要な要素に絞る
- 対象プラットフォームの HIG や標準 UI 慣習から不必要に逸脱しない

### コンポーネント設計

- 単発の見た目ではなく、再利用可能なまとまりを優先する
- 似た役割のものは、できる限り共通の考え方で扱う
- バリエーションは必要最小限にとどめ、役割の違いが明確に分かるようにする
- 新しい部品は、既存の考え方で対応できない場合にのみ追加する
- 部品名や分類は、画面固有ではなく役割に基づいて考える
- 状態の扱いは一貫させる
- `Component Gallery` は画面デザイン時に再利用する完成版の正本とし、画面側で別デザインを発明しない
- 画面デザイン内のコンポーネントは、`Component Gallery` と同一デザインであることを前提にする
- 標準的な図像がある操作やオブジェクトは、明示指示がなくても icon set を使うことを基本とする

### 一貫性と言語

- 名称は実装都合ではなく意味に基づいて決める
- 同じ概念には同じ言葉を使う
- 違う概念に同じ言葉を使わない
- ラベルや名称は短く、意味が明確で、文脈に依存しすぎないものにする
- 文言は曖昧さを減らし、認識しやすさを高めるために使う
- 内部用語をそのまま利用者向け表現に持ち込まない
- 似た情報は似た見せ方で提示する
- 似た行動は似た位置、似た表現、似た流れで提示する
- 例外は最小限にとどめる

### アクセシビリティと判断基準

- 色だけに意味を依存させない
- 強調や違いは複数の手がかりで伝える
- 読みやすさ、階層、状態の分かりやすさを基本要件として扱う
- キーボード操作やフォーカスの視認性を軽視しない
- エラーや補助情報は気づける形で提示する
- 一部の利用者だけが理解できる設計にしない
- 分かりやすさ、一貫性、再利用性を優先する
- アイコンやジェスチャに意味を持たせる場合は、対象プラットフォームの標準的な理解と衝突しないことを確認する
- 派手さより静かな使いやすさを優先する
- 思いつきより構造的な妥当性を優先する
- 見た目の美しさだけでなく、情報設計、優先順位、運用時の現実性、意味のある色設計を重視する

### 制約

- 装飾のためだけの表現を増やしすぎない
- 構造的な意味を持たない複雑さを持ち込まない
- 一度しか使えない見せ方を安易に増やさない
- 画面ごとの都合だけで命名や構造を決めない
- 重要度、状態、行動の違いが曖昧になる設計を避ける
- wireframe、layout、component、screen の各段階を混在させない
- `Component Gallery` 未完成のまま `screen design` に進まない
- `screen design` 中に不足が見つかった場合は、先に `Component Gallery` を更新してから戻る
- `Component Gallery` 完成後の文書照合を省略したまま `screen design` に進まない

## 制作工程

### 固定順序

1. `wireframe`
2. `component gallery`
3. `screen design`

### 各段階の責務

- `wireframe`: 画面責務、情報構造、状態遷移を低忠実度で確定する
- `component gallery`: このプロダクトで使う全コンポーネントを、色、サイズ、状態、操作結果まで含めて完成状態で確定する
- `screen design`: `component gallery` で確定済みのコンポーネントだけを使って画面を組み立てる

### Component Gallery 完了後の確認

- `Component Gallery` 作成後は、`screen design` へ進む前に文書群を再帰的に見直す
- 確認対象は `DESIGN.md`、`foundations.md`、`layouts.md`、`components.md`、`ui-patterns.md`、`screens.md`、`tokens.md`、`checklist.md` とする
- 確認観点は、抜け漏れ、責務のずれ、状態不足、画面との不整合、ギャラリー側に寄った独自解釈の混入とする
- `Component Gallery` と文書が食い違う場合は、先に文書へ還元してから次段階へ進む
- この確認で差分が見つかった場合は、成果物と文書のどちらを正とするかを判断し、必要な側を更新する

### 禁止事項

- `wireframe` の段階で完成画面の見た目を決めない
- `screen design` の段階で新しいコンポーネントや状態を先に作らない
- `screen design` を優先して `component gallery` の不足を後回しにしない

## 下位文書との関係

- foundations はデザインシステムの値とルールを扱う
- layouts は画面内のゾーン構成とレスポンシブ時の変化を扱う
- components は再利用部品の定義を扱う
- ui-patterns は複数の画面で繰り返し使う振る舞いと構造を扱う
- screens は画面単位の責務と構成を扱う
- tokens は実装可能な値を扱う
- checklist は設計とレビューの抜け漏れ確認を扱う
