# DESIGN.md

## この文書の役割

この文書は、`docs/design/` 配下のデザイン文書群における上位原則と入口を定義するための文書である。  
ここでは、デザイン原則、文書群の責務、参照関係を扱う。  

## 目的

- このプロジェクトにおけるデザイン判断の土台を明文化する
- 人と AI が同じ前提でデザイン判断できる状態をつくる
- foundations、components、patterns、screens、tokens、checklist へ展開するための共通前提をそろえる

## 適用範囲

- この文書は、デザイン判断の基準とデザイン文書群の構成を定義する
- この文書は、個別画面の完成レイアウトや個別コンポーネントの詳細仕様を直接定義しない
- 下位のデザイン文書は、この文書の原則に従う

## 文書構成

- `docs/design/DESIGN.md`: 上位原則と入口
- `docs/design/workflow.md`: 前提条件、必須成果物、工程、ゲート
- `docs/design/foundations.md`: テーマ、色、タイポグラフィ、余白、レイアウト、装飾、文言
- `docs/design/components.md`: コンポーネント定義
- `docs/design/ui-patterns.md`: UI パターン定義
- `docs/design/screens.md`: 画面一覧、責務、画面設計
- `docs/design/tokens.md`: 実装用トークン
- `docs/design/checklist.md`: 抜け漏れ確認用チェックリスト

## デザイン原則

### 基本原則

- 見た目より先に意味を整理する
- 装飾より先に構造を整える
- 変化より先に一貫性を優先する
- 印象より先に理解しやすさを優先する
- 局所最適より全体整合を優先する
- 理想化されたモックではなく、実際に使われるプロダクトとして自然な UI を前提にする

### 情報設計と構造

- 情報は実装都合ではなく意味のまとまりで整理する
- 主要な情報はすぐ把握できる位置と粒度で提示する
- 補助的な情報は主目的を妨げない形で提示する
- 構造は一目で大枠を把握できることを優先する
- 情報として必要な差分は省略しない
- 意味差を消すほど表現を抑えない

### UI と UX

- 利用者が今どこにいて、何ができて、次に何が起こるかを理解できるようにする
- フィードバックは不安を減らし、状況理解を助けるものにする
- 実運用を想定し、長いテキスト、欠損、ゼロ件、異常値があっても破綻しにくい体験にする
- 強調は装飾ではなく重要度に基づいて行う

### コンポーネント設計

- 単発の見た目ではなく、再利用可能なまとまりを優先する
- バリエーションは必要最小限にとどめる
- コンポーネント、UI パターン、状態を混同しない
- コンポーネントの粒度は先に定義する
- カードや独立した面は、意味、操作、状態、文脈を持つ場合にのみ使う
- 余白、階層、罫線で構造を見せることを優先する
- 状態は親コンポーネントに従属させる
- 状態は実務上そのコンポーネントで実際に起こりうるものだけを採用する

### 一貫性と言語

- 同じ概念には同じ言葉を使う
- 違う概念に同じ言葉を使わない
- 文言は曖昧さを減らし、認識しやすさを高めるために使う
- 表記は特段の理由がない限り日本語ベースとする

### アクセシビリティと判断基準

- 色だけに意味を依存させない
- 強調や違いは複数の手がかりで伝える
- 読みやすさ、階層、状態の分かりやすさを基本要件として扱う
- キーボード操作やフォーカスの視認性を軽視しない
- アイコンやジェスチャに意味を持たせる場合は、対象プラットフォームの標準的な理解と衝突しないことを確認する
- 派手さより静かな使いやすさを優先する

### 制約

- 装飾のためだけの表現を増やしすぎない
- 構造的な意味を持たない複雑さを持ち込まない
- グラデーションや奇抜な美術的演出を優先しない
- 重要度、状態、行動の違いが曖昧になる設計を避ける

## 下位文書との関係

- foundations は見た目の基礎ルールを扱う
- components は部品定義を扱う
- ui-patterns は複数画面で再利用する UI パターンを扱う
- screens は画面設計を扱う
- tokens は実装可能な値を扱う
- checklist は抜け漏れ確認を扱う
